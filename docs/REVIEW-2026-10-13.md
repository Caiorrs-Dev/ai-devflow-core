# ai-devflow-core: code review and assessment

- **Date:** 2026-10-13
- **Scope:** every tracked file (81 files: `bin/ai-flow.mjs`, `test/`, `core/`, `presets/`, `machine/`, CI, README).
- **Version reviewed:** `0.3.0` (`ae9bfe3`).
- **Method:** full read of every file, `npm test` (18/18 pass), and live reproduction of each bug marked **[verified]** against a temporary project.

## Summary

The project is small, coherent and well written. The CLI is about 690 lines with no
dependencies. The layering model (`managed` / `seed` / `blocks` / `vars` / `roles` /
`skills`) is simple and clearly documented. The workflow templates show real
operational knowledge: required checks that report on docs-only PRs, fail-open path
filtering, back-merge without force-push, PR-title linting via `env` instead of
inline interpolation. The role briefs are concise and have a clear handoff contract.

The main weaknesses:

1. **Lifecycle gaps in the sync model.** There is no record of what was synced, so
   the tool cannot delete orphans, cannot let a project opt out of a seed, and
   cannot tell which upstream version a project is on. One README instruction is
   impossible to follow because of this (see B1).
2. **The `react-native-firebase` preset is half-finished.** It inherits Vitest-only
   content from `node-ts` that it cannot remove, its requirements are incomplete,
   it has no test coverage, it is missing from the README, and it leaks
   project-specific text.
3. **Skills subcommands have correctness bugs** around `--dry-run`, failure
   handling and argument parsing.
4. **Input validation is thin.** Bad config, missing option values and malformed
   JSON produce raw Node errors without context.
5. **The repository does not apply its own standards** (no lint, no release flow,
   no license, unpinned actions).

Severity scale: **High** = wrong behavior a user will hit; **Medium** = wrong in
some setups, or a missing safety net; **Low** = polish.

## 1. Bugs

### B1. Deleted seeds come back on every sync, and `check` fails forever — High [verified]

`reconcile()` treats any missing seed as drift and re-creates it:

```js
for (const [rel, text] of plan.seed) {
	if (read(rel) !== null || plan.managed.has(rel)) continue;
	report.drift.push(`missing seed: ${rel}`);
```

But the README tells users to delete one:

> If your `package.json` already has a `lint-staged` field, delete the seeded
> `.lintstagedrc.json` so lint-staged reads only one config.

Reproduced: after `rm .lintstagedrc.json`, `ai-flow check` reports
`drift: missing seed: .lintstagedrc.json` (exit 1) and `ai-flow sync` writes it
again. The same applies to any seed a project does not want (`knip.json`,
`build-check.yml`, issue templates, etc.). "Written once" is not what the code does;
it is "written whenever missing".

**Fix options:** add `disabledSeeds: [...]` to `.ai-flow.json` (smallest change), or
record created seeds in a state file (see M1) and only create them on first sync.

### B2. `skills add` / `skills remove` write `.ai-flow.json` even with `--dry-run` — High [verified]

`saveConfig()` runs before `installBySource` / `runSkills`, and `dryRun` is only
passed to the runner. Reproduced: `ai-flow skills add foo/bar baz --dry-run`
printed `would run: …` and still added `"foo/bar": ["baz"]` to `.ai-flow.json`.

**Fix:** skip `saveConfig()` when `options.dryRun`. Also consider saving only after
a successful install, so a failed `add` (bad source, network error) does not leave
a config entry that makes `check` fail.

### B3. `installBySource` stops after the first failed source — Medium [verified]

```js
status ||= runSkills(args, { cwd, dryRun });
```

`||=` short-circuits: once `status` is non-zero, `runSkills` is never called again.
Reproduced with `AI_FLOW_SKILLS_CMD=false`: only the first source ran, the other two
were skipped with no message. This may be intended (fail fast), but then it should
say so; as written it looks like "run all, report worst".

**Fix:** either `const code = runSkills(...); status ||= code;` (run all), or break
explicitly and print which sources were skipped.

### B4. Wrong symlink type for `AGENTS.md` / `GEMINI.md` — Medium (Windows)

```js
symlinkSync(expectedTarget, linkPath, "dir");
```

The target `CLAUDE.md` is a file. The `type` argument is ignored on POSIX but used on
Windows, where `"dir"` creates a directory symlink to a file, which is broken. On
Windows, symlink creation also needs Developer Mode or admin rights, and Git may
check symlinks out as plain text files (`core.symlinks=false`), which then show up as
the "foreign" warning on every run.

**Fix:** use `"file"`. On `EPERM`, fall back to a small pointer file or a copy, and
document Windows behavior.

### B5. `npx` cannot be spawned on Windows; command string split on spaces — Medium

- `spawnSync("npx", …)` without `shell: true` fails on Windows (the binary is
  `npx.cmd`).
- `AI_FLOW_SKILLS_CMD.split(" ")` breaks any path that contains a space (for example
  a Node install under `C:\Program Files\` or a macOS `Application Support` path).
  The test stub uses `process.execPath`, so tests pass only when that path has no
  space.

**Fix:** resolve `npx.cmd` on `win32`; accept `AI_FLOW_SKILLS_CMD` as a JSON array, or
parse it with a quote-aware splitter.

### B6. `react-native-firebase` gets Vitest instructions and Vitest-only checks — High [verified]

Blocks are **concatenated** across layers, never overridden, and `requires` and
`skills` are **unioned**. So an RN project gets:

- `CLAUDE.md` with `## Stack: Node + TypeScript` saying
  "Unit tests with Vitest in quiet mode: `npm test -- --silent`", followed by
  `## Stack: React Native + Firebase`. The agent reads contradictory rules.
- A warning `package.json does not depend on vitest`, plus `knip`, Biome, etc., that
  it cannot silence because an extending preset cannot remove a parent requirement.
- The `antfu/skills: vitest` skill installed into a Jest project.
- The `node-ts` `knip.json` seed (`src/main.ts`, `src/main.tsx`, `src/index.ts`
  entries; RN apps typically start at `index.js` / `App.tsx`).
- The `node-ts` `build-check.yml`, which runs `npm run build`. RN apps usually
  have no `build` script; the preset sets `commands.build` to `npx tsc --noEmit`,
  but the workflow does not use that var.

**Fix:** let a layer replace a block (for example, a preset's
`blocks/stack-preset.md` replaces the parent's unless it opts into appending), and
add `requires.remove` / `skills` removal at the preset level. Or extract a neutral
`node-base` preset that both `node-ts` (Vitest) and the RN preset (Jest) extend.

### B7. `react-native-firebase` does not require what its workflows run — Medium [verified]

The RN `test.yml` seed runs `@@commands.testRules@@` (`npm run test:rules`), and the
role briefs run it too, but `preset.json` requires only `test`. No warning tells the
user that `test:rules`, `@firebase/rules-unit-testing` or `firebase-tools` is
missing. The Vite preset requires all three.

**Fix:** copy the Vite preset's `requires`.

### B8. Unknown, missing or malformed input gives raw Node errors — Medium [verified]

| Input | Output |
|---|---|
| `.ai-flow.json` = `{}` | `The "path" argument must be of type string. Received undefined` |
| invalid JSON in `.ai-flow.json` | `Expected double-quoted property name in JSON at position 21` (no file name) |
| `ai-flow sync --dir` (no value) | `The "paths[0]" argument must be of type string. Received undefined` |
| `ai-flow --help` | `Unknown option: --help` |
| `roles.json` entry without `tools` | `Cannot read properties of undefined (reading 'join')` |

Also silent cases: a typo in `disabledRoles` or `disabledSkills`, an unknown
top-level key in `.ai-flow.json`, and `skills global <name>` with a name that is not
in the manifest (installs nothing, exits 0).

**Fix:** a small validator for `.ai-flow.json` (required `preset`, known keys, arrays
of strings, warn on unknown role/skill names); `readJson` that wraps errors with the
file path; `parseArgs` that rejects a flag with no value; `--help`, `-h`,
`--version`.

### B9. `node-ts` `test.yml` ignores `commands.test` — Low

The unit-test step hardcodes `npx vitest run --changed HEAD^1 --passWithNoTests`
while the RN workflow uses `@@commands.test@@`. A project that overrides
`commands.test` (for example to add a config file) gets a CI command that differs
from what the quality gate runs locally. Add a `commands.testChanged` var or render
`@@commands.test@@` with the changed-files flag.

### B10. Smaller code-level issues — Low

- `lookup()` reads inherited properties: `@@constructor@@` resolves to `Object` and
  renders `function Object() { [native code] }` instead of failing as unknown. Use
  `Object.hasOwn(node, key)`.
- `deepMerge()` copies an own `__proto__` key from parsed JSON into `merged`, which
  sets the merged object's prototype. The input is local config, so the risk is low,
  but skipping `__proto__`, `constructor` and `prototype` is one line.
- `render()` does no escaping. A var containing `"` or a newline breaks JSON seeds
  (`release-please-config.json` uses `@@release.packageName@@`), and a var with `:`
  or `#` can break YAML. Validate rendered `.json` files with `JSON.parse` before
  writing, and parse rendered YAML in tests.
- `withManagedNote()` silently drops the note for Markdown that starts with `---` but
  has no closing `---`.
- `applyBlocks()` uses the first `start` and the first `end` marker independently;
  duplicate markers, or an `end` before the first `start`, are not reported as
  malformed.
- `snapshotGlobalSkills()` groups lock entries with no `source` under the key
  `"undefined"`.
- `missingSkills()` matches lock entries by name only. Two sources that ship a skill
  with the same name (`react` is a likely collision), or a skill installed from a
  different source than the preset asks for, count as "locked".
- `printReport()` in dry-run prints `would write: skills not in skills-lock.json…`,
  but `sync` never installs skills.
- Line endings: on Windows with `core.autocrlf=true`, managed files check out as
  CRLF and every one shows as `modified`. Normalize line endings before comparing,
  or ship a `.gitattributes` seed.

## 2. Missing features

### M1. A sync state file — High

There is no record of what `ai-flow` wrote or which version wrote it. This one gap
causes several problems:

- **Orphans are never removed.** README: "`sync` never deletes files". When a managed
  file is renamed or removed upstream, or a role is disabled, the old file stays in
  every project. For `.claude/agents/<role>.md` this means an agent the
  orchestrator still sees.
- **Seeds cannot be "once"** (see B1).
- **No version pinning in CI.** The README recommends
  `npx github:Caiorrs-Dev/ai-devflow-core check` in CI. Without a tag, CI checks
  against the latest `main`, so any upstream change fails every project's CI until
  someone syncs. With a tag, nothing tells the project which version it is on.

**Proposal:** write `.ai-flow.lock.json` (committed) on each sync, containing the
`ai-devflow-core` version, and each managed and seeded path with a content hash.
Then:

- `sync` removes managed files that are in the lock but no longer in the plan (and
  reports them);
- seeds are created only when they are not in the lock;
- `check` warns when the running CLI version differs from the lock version, and
  `check --version-from-lock` can fail on it;
- a managed file whose content differs from both the lock hash and the new upstream
  content can be reported as "locally edited, will be overwritten", which is a
  more useful message than `modified`.

### M2. Opt-out of individual managed or seed files — Medium

Only role briefs can be disabled. A project that does not want the back-merge
workflow, the Husky hooks or the commitlint workflow has to delete them and live
with drift. Add `disabledFiles: ["<rel path>", …]` covering managed and seed files.

### M3. Preset composition — Medium

`extends` takes one parent. The two Firebase presets duplicate
`rules-auditor.md` (byte-identical), `roles.json` (rules-auditor identical),
`commands.testRules`, `extraChecks`, the rules job in `test.yml`, and most of the
`extra.*` text. A future `node-firebase-functions` or `nextjs-firebase` preset would
copy them a third time.

**Proposal:** `extends` accepts an array (or add `mixins`), and extract a
`firebase` layer (rules auditor, rules test job, rules vars) and a `react` layer.
Combine with B6's block override so a layer can replace rather than append.

### M4. Strict mode for `check` — Medium

`check` exits 0 with warnings: missing `CLAUDE.md` markers, foreign
`AGENTS.md`, missing scripts and dependencies. In CI these are exactly the things
worth failing on. Add `check --strict` (warnings are errors) and machine-readable
output (`--json`).

### M5. `ai-flow doctor` (repository setup verification) — Low

The README's "Repository setup" section is a manual checklist: `stage` branch,
branch protection, required check names, `BACK_MERGE_TOKEN`,
`RELEASE_PLEASE_TOKEN`, squash merge. Much of it is checkable with `gh api`
(branch exists, protection requires the named checks, secrets exist, squash merge
allowed). A `doctor` command would catch the most common setup error: required
check names that do not match job names.

### M6. Missing command surface — Low

- `--help`, `-h`, `--version`.
- `ai-flow diff` (show the content diff for drifted managed files, not only the
  path).
- `ai-flow init --force` / `--preset` change for an existing project (today the
  user must edit `.ai-flow.json` by hand; that works, but is undocumented).
- `ai-flow roles` to list the resolved roles with model and tools.

### M7. JSON Schema for `.ai-flow.json` and the layer files — Low

Ship `schema/ai-flow.schema.json` and have `init` write `"$schema"`. Editors then
autocomplete `vars` keys and flag typos in `disabledRoles`. The same schema can
drive the validator in B8. Optional schemas for `preset.json`, `roles.json` and
`skills.json` would catch layer mistakes at test time.

### M8. Workflow gaps in the cycle — Low

- No role or documented flow for the **promotion** PR (`stage` → `main`), even
  though the back-merge and release-please workflows depend on it.
- The ADR index is a table that every planner appends a row to. Parallel PRs
  conflict on the last line of the same file. Consider generating the index (a
  script or a managed block), or ordering rows so appends land in different places.
- `next-adr-number.sh` uses `git ls-tree "$ref" "$dir/"`, whose path is relative to
  the current directory. Run from a subdirectory, it finds nothing and returns
  `0001`. Add `cd "$(git rev-parse --show-toplevel)"`.
- The seeded `.release-please-manifest.json` starts at `0.1.0`. A project adopting the
  cycle with an existing version gets a wrong first release. Seed it from
  `package.json` `version`, or warn when they differ.

## 3. Preset and template content

### P1. `react-native-firebase` preset — High

Besides B6 and B7:

- Not in the README presets table or the Skills table.
- Not covered by the `init syncs a full project for every preset` test, which loops
  over a hardcoded list of two presets. Use `listPresets()` instead so a new preset
  is tested automatically.
- No `skills.json`. Candidates: React Native / Expo skills, `vercel-react-best-practices`.
- `ui-auditor.md` leaks a specific project: "`Operate` (pet management, forms)".
- `ScreenWrapper` is named as a requirement in the stack block, `extra.*` vars and
  `ui-auditor.md`. That is one project's component, not an RN convention. Make it a
  var (`ux.safeAreaComponent`) or describe it generically.
- The unit-test job always runs the full suite (no changed-files mode), unlike the
  other presets. That may be deliberate for Jest; say so in a comment.

### P2. Coupling to personal tooling — Medium

The shared rules and every wrapper assume tools that are not part of the project:

- `rtk` prefix, CodeGraph (`.codegraph/`, `codegraph explore`), and the
  `mcp__codegraph__codegraph_explore` tool listed in the `tools` of six roles. In a
  project without that MCP server, the tool name is dead weight in the wrapper,
  and the brief text tells the agent to use something that does not exist.
- `core/skills.json` makes every project install
  `cursor/plugins: thermo-nuclear-code-quality-review`, and `review.skillPath`
  points at it.
- `machine/global-skills.json` is one person's machine setup, shipped in the npm
  `files`. That is fine for a personal repo but unusual for a package meant for
  "any repository".

**Proposal:** move tool-specific lines behind vars (`tools.shellPrefix`,
`tools.codeSearch`, `roles.extraTools`), defaulting to empty in `core`, and set them
in a personal overlay (`.ai-flow.json` vars or a `personal` preset). Keep
`machine/` out of the published `files`, or document it as an example.

### P3. Workflow templates — Low

- Action pinning is inconsistent: `release-please-action` is pinned to a SHA,
  `dorny/paths-filter@v3`, `actions/checkout@v7`, `actions/setup-node@v7`,
  `actions/setup-java@v5` are not. Third-party actions (`dorny/paths-filter`) are the
  higher supply-chain risk. Pin them all to SHAs, and seed a Dependabot or Renovate
  config for `github-actions` so the pins get updated.
- `commitlint.yml` runs `npm ci` only to get commitlint. That is the full project
  install on every PR edit (including title edits). Acceptable, but
  `npm ci --ignore-scripts` would be faster and safer.
- No `timeout-minutes` on any job; a hung emulator job runs for the 6-hour default.
- `back-merge.yml` uses a global concurrency group `back-merge`; fine for one
  repository, but name it `back-merge-${{ github.repository }}` if reused.
- No `.github/dependabot.yml` seed and no CODEOWNERS seed, though both fit the
  "repository setup" scope.

### P4. Seeds — Low

- `biome.json` `files.includes` is `src/**`, `test/**`, `tests/**`. Config files at
  the root (`vite.config.ts`, `*.config.mjs`) and `scripts/**` are not linted, but
  `lint-staged` passes them to Biome, which then ignores them silently
  (`--no-errors-on-unmatched`). Either include them or document the choice.
- `biome.json` pins the schema to `2.5.12`; that goes stale. Note it in the README
  or render it from a var.
- Issue templates use `.md` templates. GitHub issue forms (`.yml`) give required
  fields, which suits the product-owner's "acceptance criteria" rule better.

## 4. Tests

The suite is good for its size: it runs the real CLI in temporary directories and
stubs the `skills` CLI in a clean way. Gaps:

- **Presets:** only 2 of 3 are exercised (P1). Add a test that iterates
  `listPresets()` and asserts no `@@` remains in any written file.
- **Rendered output validity:** parse every rendered `.json` with `JSON.parse` and
  every `.yml` with a YAML parser (would need one dev dependency, or a minimal check);
  run `actionlint` and `shellcheck` in CI on the rendered output of each preset.
- **Untested paths:** preset cycle detection, multi-level `extends`,
  `withManagedNote` for each file kind, foreign `AGENTS.md` warning, missing
  markers warning, `sync --dry-run` writes nothing, `vars`, `presets`, unknown
  command exit code, `init` when `.ai-flow.json` exists, role override merge
  (a preset changing a core role's model).
- **Regression tests for the bugs above:** B1 (deleted seed), B2 (dry-run config),
  B3 (multiple failing sources), B8 (bad config messages).
- **Platform:** CI runs only `ubuntu-latest`. Add `windows-latest` and `macos-latest`
  to the matrix; B4 and B5 would surface immediately.
- **Assertion quality:** `applies project vars and disabled roles` matches
  `/test\s+labels in Brazilian Portuguese/`, which depends on line wrapping in the
  brief. Prefer asserting on the rendered var value.

## 6. Suggested order of work

1. **Quick fixes (one PR each, small):** B2, B3, B4 (`"file"`), B7, `--help`, the
   `readJson` file name, the `next-adr-number.sh` `cd`, README preset table and tag.
2. **Seed opt-out:** `disabledSeeds` / `disabledFiles` (B1, M2), with tests.
3. **Config validation and schema:** B8 and M7 together.
4. **RN preset repair:** block override and requirement removal (B6), then P1
   cleanup and test coverage via `listPresets()`.
5. **State file:** `.ai-flow.lock.json` with version, hashes, orphan removal and
   version check (M1). This is the largest item and the one with the most leverage.
6. **Composition:** `mixins` / array `extends` and a shared `firebase` layer (M3).
7. **Hardening:** cross-platform CI, rendered-output validation, action pinning,
   repository hygiene items.

## 7. What is already good (keep it)

- Zero runtime dependencies, Node built-ins only, `node --test`.
- `@@var@@` delimiter chosen so GitHub Actions `${{ }}` passes through; unknown
  vars fail the sync and name the source file.
- Multi-line var indentation handling in `render()`.
- Managed notes placed after front matter and shebangs, so files stay valid.
- `package.json` is never edited; requirements become warnings.
- Workflows: fail-open path filtering, required checks that report on skipped jobs,
  PR title linted through `env` (no script injection), back-merge that skips equal
  trees and never force-pushes, comments that explain every non-obvious choice.
- Role briefs: short, imperative, with explicit "Never" sections and one handoff
  format; the orchestrator's stop conditions (two failures, at most two review
  rounds) are clear.
- Third-party skills referenced by source and locked, instead of vendored.

## 9. Follow-up review (2026-10-14)

A second pass over 0.4.0 found the issues below. Each was fixed with a test
that fails on the version before it.
